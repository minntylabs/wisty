EXTERNAL TEXT-FILE CHANGE DETECTION, 2026-08-08
=================================================

Two rounds of correction to the feature described in
external-change-detection-review.txt: the first against the initial
implementation, the second against the first round's own fixes. The second
round is the more instructive one — every fault in it sat in what happens
after the operation the baseline describes has already succeeded, which is
the part no test was watching.

FIRST ROUND — against the initial implementation

The implementation recorded a text file's metadata after loading, compared
asynchronous focus checks against mutable document state, and allowed Reload
from Disk to discard dirty edits immediately.

1. A text-file version is cleared before every plain-text open. This prevents
   a failed replacement open from retaining the previous document's baseline.

2. Version checks capture the path, baseline and generation before awaiting
   filesystem metadata. A result is discarded when another document has been
   opened in the meantime.

3. A dismissed conflict records the external version it saw. A later changed
   version or deletion reopens the banner instead of remaining hidden until
   Save.

4. Metadata lookup failures are no longer treated as a missing file, so a
   fault cannot silently omit the backend's expected-source validation.

5. Reload from Disk now runs through the existing discard confirmation flow,
   so it cannot silently throw away dirty editor content.

SECOND ROUND — against those fixes

6. Fix 4 took deletion with it. Tauri's stat rejects for a deleted path
   exactly as it does for a permission fault, so refusing to swallow the
   rejection stopped deletion returning null and made the "deleted" conflict
   unreachable: silent on focus, a bare failure on Save. The two are now told
   apart by asking whether the path is still there. This needs fs:allow-exists
   in the capability — neither fs:read-all nor the explicit fs:allow-stat
   covers the exists command, and an unanswerable check is read as "still
   there" so the original fault wins, which would have reinstated the whole
   regression in the built app.

7. Fix 3 left a banner standing after the conflict it described was gone. A
   file restored to the version the document was opened at now retracts it,
   and a file that returns after a deletion is judged afresh rather than
   against the version seen before it went away — a dismissal of the old
   version was not consent to the new one.

8. Taking a baseline never throws. It happens after the file is already open
   or already written, so its failure says nothing about whether that
   succeeded, and reporting it as one told the user a save had failed when it
   had not — and put "Unable to open file" above a document it had opened.
   The failure is recorded instead, and Save is the one operation that acts on
   it: it retakes the baseline, and refuses only if that fails again. A single
   unlucky stat no longer locks the document until it is closed and reopened.

9. A deleted file marks its document unsaved. The editor then holds the only
   copy of the text, and leaving the document clean let it be closed away
   without a prompt — the one case where detecting the conflict and doing
   nothing about it was worse than not detecting it.

10. Saving guards what it writes back to the document. Opening a file does not
    cancel a save already streaming, so a save that landed after the document
    was replaced marked the new document saved at the old one's revision.

WHAT THE TESTS DO NOT SEE

Both round-two regressions in the filesystem layer — the deletion contract and
the missing capability — were invisible to the suite, because the lifecycle
tests fake fileIo and the unit tests mock @tauri-apps/plugin-fs. A fake that
still models the old contract is indistinguishable from a passing test. Any
further change to how getTextFileVersion reports a missing file needs checking
against the plugin's real behaviour and against capabilities/default.json, not
only against the fakes.

RESIDUAL LIMITS

The backend rechecks metadata immediately before rename, but portable POSIX
and Windows APIs do not offer rename-if-this-path-still-has-this-version.
An uncooperative writer can therefore still win the tiny interval between the
check and rename.

Text versions intentionally use size, mtime, device and inode. They can miss
an in-place same-size edit whose timestamp is unchanged or too coarse. A full
content digest would close that case but adds a second full read before every
large-file save; this is a documented metadata-only tradeoff. On Windows
device and inode are absent, leaving size and mtime alone.

A document opened from text handed to Wisty rather than read from disk —
openFileFromTextAtPath — records no baseline, so it has no external-change
detection until it is saved.

Focus-triggered checks do not observe changes while Wisty remains focused. A
filesystem watcher would be the future enhancement if immediate notification
becomes necessary.
